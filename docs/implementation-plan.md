# AIS3 implementation plan

Each step ends with working software, automated checks where meaningful, and a manual review checklist with testing instructions. For Step 10 and every subsequent step, leave changes uncommitted, stop verification servers, and stop for manual review before proceeding. Steps 1–14 are approved and committed (Step 14: `f7c59f8`). Step 15 prepares the release and instructions for manual deployment, as requested; changes remain uncommitted for review. The actual production cutover remains an operator action.

Future steps may be refined at their start. Do not implement a later step before its review gate. Step 5 includes the minimum mail integration needed to review registration end to end, as approved after Step 4. Step 6 reuses that sender for recovery; Step 12 verifies the RabbitMQ publication boundary; delivery operations belong to AliceMailService. Recovery, profile, and the live administration shell are approved. User reading/search/details are approved. Account operations are approved. Claims and scopes are approved. Clients are approved. Mail publication is approved. Staging and hardening are approved. AIS2 migration rehearsal is approved and committed as `f7c59f8`. Step 15 is authorized as release preparation and manual deployment instructions. See the [Step 15 review](reviews/step-15.md).

Step 6 uses the existing Identity schema. The profile keeps the sign-in email read-only as shown in the approved UI; changing the email address is outside this step. See the [Step 6 review](reviews/step-6.md) for that completed step.

Step 7 reads existing tables without schema changes: live session identity, overview counts, five recent registrations, and up to six application summaries. Step 8 connects overview links to the live directory/details. Client editing, scopes, and account operations remain in their separate steps.

Step 8 uses case-insensitive substring search across first/last/screen names and email. Whitespace-separated terms are ANDed, in any order; SQL wildcard characters are escaped. A single GIN expression index and `pg_trgm` extension live in `PopulateSchema.sql`, which is explicitly applied to fresh databases and AIS2 restores. No table/column changes, generated schema edits, search functions, or tracked migrations are needed. Query/filter/sort/page state is URL-backed; Step 8 delivered read-only details and claims/security summaries. The approved search contract is unchanged by Step 9.

Step 9 carries forward AIS2's create/edit/reset/delete account functions and adds explicit lock/unlock controls. Creating an account sets email as username, confirms it after administrator verification, and grants no claims. Editing changes only names and confirmation; email remains read-only. Passwords use Identity policy. Security changes rotate the security stamp and revoke OIDC tokens/authorizations transactionally; deletion removes Identity data and retains revoked protocol records. Self lock/delete/unconfirm is rejected, and administrative writes serialize with a fresh actor check to prevent concurrent administrators disabling each other. No schema, SQL or mail changes are needed. Step 10 adds claims/scopes without changing this behavior. Step 11 adds client administration.

Step 10 reuses the Step 9 serialization/actor boundary for user claims and scopes. Claim changes rotate security stamps and revoke grants transactionally; own last-admin removal is rejected. Custom scopes use the existing OpenIddict claims property/resources, preserve unrelated imported metadata, have immutable names, and cannot be deleted while permitted by a client or referenced by a valid authorization. Standard definitions remain read-only. Scope edits affect newly issued tokens and userinfo without changing existing JWTs or client permissions. No schema/configuration/dependency changes are needed. Step 10 is approved and committed as `5b469b0`.

Step 11 uses the same administration boundary for public/confidential authorization-code client registration, settings, secret/type changes and deletion. IDs remain fixed; supported fields preserve unrelated imported metadata and existing secret hashes. New public clients and public-client settings saves require PKCE. Newly added callbacks must use HTTPS or HTTP loopback; existing imported callbacks can be retained. Security-related settings and credentials revoke client grants transactionally, while display-name-only changes retain them. Unsupported imported profiles are read-only. The standalone review client now accepts a client ID, optional secret and requested scopes. No schema, SQL, application configuration or dependency changes are required. Step 11 is approved and committed as `07e10f0`.

Step 12 is limited to AIS3's RabbitMQ publication responsibility. The existing Step 5/6 sender, templates and account failure behavior remain; safe logs distinguish confirmed, failed and cancelled attempts, and focused tests verify publication with no consumer, channel-failure recovery and no automatic replay. SMTP delivery, retries, failed queues and consumer operations belong to AliceMailService. No Mail UI/API, diagnostic command, metrics subsystem, cross-service harness, schema/SQL, dependencies or private settings changes are included. Step 12 is approved and committed as `954b5bd`.

Step 13 enables explicitly configured Staging/Production hosting with persistent encrypted Data Protection keys, two persistent application certificates, one-hop trusted proxy handling with loopback defaults and optional explicit overrides, host/origin validation, browser security headers and safe request/error logging. The required `Application:CertificateFolder` holds two fixed-name passwordless PFX files, generated when missing and reused unchanged thereafter; newly generated certificates are valid through year 9999. The OpenIddict encryption certificate also protects the Data Protection keys stored in the same folder's automatically created `keys` subdirectory, with no separate path setting. Linux Nginx/systemd examples and a deployment/rollback guide cover a single instance with isolated staging data. Automated tests rehearse restart/key continuity and reject unsafe settings; actual Linux permissions, public TLS and the manual end-to-end checklist remain deployment review checks. No schema/SQL, dependencies, private settings or mail-delivery features change. Step 13 is approved and committed as `c3112fa`.

Step 14 rehearses a read-only AIS2 snapshot dump/restore into disposable databases, compares all public table counts/content fingerprints, shared catalog and sequence state, and verifies that the existing PopulateSchema.sql preserves data. Imported synthetic legacy hashes, accounts, public/confidential clients and scope claims exercise direct/admin sign-in and OIDC flows after restore. Private JSON reports and a migration/rollback guide document the evidence and remaining real-client checks. The reviewed cutover policy requires reauthentication and fresh AIS3-owned certificates/key ring; old browser/account-link/grant continuity is not promised. No production cutover, schema/SQL changes, private settings, dependencies or architecture changes are included. Step 14 is reviewed and committed as `f7c59f8`.

Step 15 is explicitly scoped to preparing the release and instructions for the user to deploy manually. It adds a clean portable release bundle with provenance/file checksums and exclusion checks, a Production settings sample/systemd override, a read-only comparison of the actual final AIS2 restore, and a cutover/recovery/operations runbook. The source account/client model, SQL scripts, architecture and approved UI remain intact; release metadata is updated and implementation-step/review banners are removed from the account and administration UI. Verify locally, stop verification servers and leave changes uncommitted for review. The final production migration, public traffic switch and operational handoff are not represented as completed by preparing the bundle.
