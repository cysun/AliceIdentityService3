Step 6 uses the existing Identity schema. The profile keeps the sign-in email read-only as shown in the approved UI; changing the email address is outside this step. See the [Step 6 review](reviews/step-6.md) for that completed step.

Step 7 reads existing tables without schema changes: live session identity, overview counts, five recent registrations, and up to six application summaries. Step 8 connects overview links to the live directory/details. Client editing, scopes, and account operations remain in their separate steps.

Step 8 uses case-insensitive substring search across first/last/screen names and email. Whitespace-separated terms are ANDed, in any order; SQL wildcard characters are escaped. A single GIN expression index and `pg_trgm` extension live in `PopulateSchema.sql`, which is explicitly applied to fresh databases and AIS2 restores. No table/column changes, generated schema edits, search functions, or tracked migrations are needed. Query/filter/sort/page state is URL-backed; Step 8 delivered read-only details and claims/security summaries. The approved search contract is unchanged by Step 9.

Step 9 carries forward AIS2's create/edit/reset/delete account functions and adds explicit lock/unlock controls. Creating an account sets email as username, confirms it after administrator verification, and grants no claims. Editing changes only names and confirmation; email remains read-only. Passwords use Identity policy. Security changes rotate the security stamp and revoke OIDC tokens/authorizations transactionally; deletion removes Identity data and retains revoked protocol records. Self lock/delete/unconfirm is rejected, and administrative writes serialize with a fresh actor check to prevent concurrent administrators disabling each other. No schema, SQL or mail changes are needed. Step 10 adds claims/scopes without changing this behavior. Step 11 client editing remains unimplemented.

Step 10 reuses the Step 9 serialization/actor boundary for user claims and scopes. Claim changes rotate security stamps and revoke grants transactionally; own last-admin removal is rejected. Custom scopes use the existing OpenIddict claims property/resources, preserve unrelated imported metadata, have immutable names, and cannot be deleted while permitted by a client or referenced by a valid authorization. Standard definitions remain read-only. Scope edits affect newly issued tokens and userinfo without changing existing JWTs or client permissions. No schema/configuration/dependency changes are needed. Leave this step uncommitted and stop for manual review before Step 11.
