# AIS3 implementation plan

Each step ends with working software, automated checks where meaningful, a manual review checklist, and an explicit stop for review. Steps 1–6 are approved and committed (Step 6: `c2b9c03`). Step 7 is implemented and uncommitted for review. Step 8 has not started.

| Step                              | Deliverable                                                                                                                                                       | Review gate                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **1 — Foundation and UI shells**  | Fresh repo and initial project shells; HTTPS dev workflow; Razor login variants/register/recovery; React shell, sample users, components; compatibility baseline. | Build and run from README; review layout and component interactions. No live authentication or data. |
| 2 — Persistence and bootstrap     | One ASP.NET Core project, standard configuration, versioned SQL schema scripts compatible with AIS2 tables, and a bootstrap command.                              | Review script-based initialization, bootstrap reruns, and unchanged AIS2 dump compatibility.         |
| 3 — Direct account login          | Real sign-in/out, cookie/session policy, admin authorization foundation.                                                                                          | Successful/failed/locked/unconfirmed sign-ins; safe redirects and unauthorized access tests.         |
| 4 — OIDC sign-in                  | Authorization code/refresh/logout flow; validated compact login context.                                                                                          | A test client completes sign-in, token renewal and logout; reject invalid clients/redirects/PKCE.    |
| 5 — Registration and confirmation | Real registration, confirmation/resend links, OIDC continuation, versioned email templates, and basic RabbitMQ/AliceMailService integration.                                                                                                     | New/duplicate accounts, valid/expired/used links, OIDC continuation, real mail handoff and publication failures.                                 |
| 6 — Recovery and profile          | One-hour reset links and password changes with session invalidation; profile name display/edit; reuse mail templates and sender.                                                                                                                      | Valid/expired/reused links, OIDC continuation, session/token invalidation, validation, and persisted profile changes.                          |
| 7 — Live administration shell     | Protected React routes/API, current administrator identity, session handling, real overview counts and bounded registration/application summaries.                                                                                               | Admin/non-admin sessions, expired-session behavior, dashboard counts.                                |
| 8 — User reading and search       | API-backed users, search/pagination/filtering and details.                                                                                                        | Representative dataset, sort/filter/page interactions, access control.                               |
| 9 — User operations               | Account editing, lockout and approved administrative operations.                                                                                                  | Validation, authorization, confirmations and persisted results.                                      |
| 10 — Claims and scopes            | Claim assignment and scope definitions.                                                                                                                           | Authorized CRUD, duplicate/error paths and resulting token claims.                                   |
| 11 — Clients                      | Client settings, redirects, secrets, scopes and PKCE.                                                                                                             | Create/edit representative clients and exercise their OIDC flows.                                    |
| 12 — Mail operations             | Delivery failure/recovery and retry operations, monitoring, and deployment verification using the Step 5 integration.                                                                                          | Operational delivery/retry/failure scenarios and deployment configuration.                                           |
| 13 — Staging and hardening        | Configuration, keys, operational logging, deployment and security review.                                                                                         | End-to-end staging flows and deployment/rollback rehearsal.                                          |
| 14 — AIS2 migration               | Rehearsed data migration with validation reports.                                                                                                                 | Compare users/clients/scopes and hashes; test migrated accounts/clients and rollback.                |
| 15 — Production cutover           | Final migration, release checks and operational handoff.                                                                                                          | Approved cutover, smoke tests and recovery plan.                                                     |

Future steps may be refined at their start. Do not implement a later step before its review gate. Step 5 includes the minimum mail integration needed to review registration end to end, as approved after Step 4. Step 6 reuses that sender for recovery; Step 12 reviews the wider delivery operations. Recovery and profile are approved; the live administration shell is implemented for review. Full user reading/search/details remain Step 8. See the [Step 7 review](reviews/step-7.md) and stop for approval before Step 8.

Step 6 uses the existing Identity schema. The profile keeps the sign-in email read-only as shown in the approved UI; changing the email address is outside this step. See the [Step 6 review](reviews/step-6.md) for that completed step.

Step 7 reads existing tables without schema changes: live session identity, overview counts, five recent registrations, and up to six application summaries. The overview does not link real records into the sample user pages. Full user search/pagination/details, client editing, scopes, and other operations remain in their separate steps. Stop before Step 8 until manual approval.
